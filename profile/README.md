<p>三四个人轮着登同一个后台，最容易出事的不是账号本身，而是「没人说得清昨天用的是哪条线」。等到要交接、要复盘、要排查某次扣费异常，才发现记录散在聊天窗口里。这篇按时间线走一遍：从下单前建台账，到开通当天、头三天分线、第一周补记录，再到第一次换人交接，每一步给出具体要留下的字段和动作。</p>
<h2>一、下单前那半天：台账先立起来</h2>
<p>线路到手再想记录，往往已经漏了关键信息。开号之前先建一张表，把「账号、线路、使用人、时间」四件事绑在一起，后面所有动作都往这张表里填。表格不用多漂亮，用在线表格或内部 wiki 都行，关键是全员可写、有时间戳。</p>
<h3>台账至少要有哪几个字段</h3>
<p>账号标识、出口 IP、归属城市、ISP 或 ASN、绑定设备或浏览器配置文件名、当前使用人、最近一次登录时间、最近一次变更原因。八个字段，少一个后面就得靠回忆补。下面这张表是字段样例，可以直接照抄列头。</p>

<h3>为什么别拿聊天记录当台账</h3>
<p>聊天记录没结构、不可筛选、换设备就丢，而且涉及账号信息时有泄露风险。台账只记环境标识和 IP 段，不记密码；密码另外放密码管理器，靠环境标识关联。这条规矩定下来，交接时就不需要传敏感信息。</p>
<h2>二、T+1 到 T+3：三个人怎么分线</h2>
<p>开通当天（T+0）先只做一件事：把线路信息原样抄进台账，包括 IP、城市、ISP、开通时间、计费档位。当天不要登录账号，让线路先静置几小时，避免刚开通就有密集请求。</p>
<h3>三个人分线路的两种排法</h3>
<p>第一种按人分：每人固定一到两条线，账号跟着人走，优点是记忆成本低，缺点是换班时要重建对应关系。第二种按账号分：每条线绑死在账号上，人不绑线，换班只是换人登同一套环境。三四个人共用后台的场景，第二种更稳，因为账号的登录地始终不变，变化只发生在人这一侧。</p>
<h3>第一次登录的错峰安排</h3>
<p>三个号不要在同一分钟内依次登录。建议间隔二十分钟以上，并且第一次登录只做三件事：看首页、发一轮短对话、退出。当天不订阅、不改设置、不批量拉历史。头一次登录留下的会话长度，往往决定了这个号后面被要求验证的概率。</p>
<h2>三、第一周：把「谁调过哪条线」变成可查记录</h2>
<h3>日志写到什么颗粒度合适</h3>
<p>不用记每一个请求，记「会话级」就够：谁、什么时候、用了哪个账号、哪条线路、做了什么类型的事（对话、订阅、改设置）、有没有异常。一次会话一行，十秒能填完。颗粒度太细没人坚持，太粗又查不出来。</p>
<h3>表格、工单还是自动化脚本</h3>
<p>四人以内用在线表格最省事；超过十人或者要按账号统计异常率，就上工单系统，把「线路变更」做成一种工单类型。再往上，直接在代理服务商的接口上拉用量日志，按环境标识对账，能省掉手工填表这一步。</p>

<h3>交接后四十八小时要复查什么</h3>
<p>看两件事：有没有出现新的验证提示；订阅扣费是否仍在原归属地完成。若出现异地判定，先核对台账里的出口是否被服务商换过，再考虑调整环境，别一上来就重建。</p>
<h3>满一个月该留哪些、删哪些</h3>
<p>留：线路变更记录、异常时间点、交接单、计费档位变更。删：明文密码、完整对话内容、带身份信息的截图。台账做一次归档，把已停用的账号标灰而不是删除，方便日后回溯。</p>
<h2>常见问答</h2>
<h3>三四个人共用一个后台，需要每人一条独立线路吗？</h3>
<p>答：看账号数而不是人数。一个账号配一条线路、一个环境，人多人少都登同一套；如果账号多于线路，才需要按账号追加。人多不是问题，同一条线上同时挂多个账号才是。</p>
<h3>台账用 Excel 会不会太简陋？</h3>
<p>答：四人以内完全够用，前提是放在共享位置并开启版本历史。真正的风险不是工具简陋，而是只有一个人会填、别人不敢动。</p>
<h3>换人之后登录地变了，会被判定异常吗？</h3>
<p>答：出口不变、设备环境不变的前提下，只是操作者换了，通常不会有额外提示。真正会引起注意的是出口城市跳变或设备指纹全换。</p>
<h3>线路中途被服务商更换，台账怎么处理？</h3>
<p>答：新增一行而不是覆盖旧行，写上变更原因和生效时间。保留历史行，排查扣费异常时才能对上当时用的是哪条。</p>
<h2>合规提示</h2>
<p>团队协作中的账号与线路记录，应仅用于内部运维和故障排查，不得用于收集他人信息或规避平台规则。</p>
<p>台账中避免存放密码、证件、对话原文等敏感内容；确需保存的，应按内部数据分级要求加密存放并限制访问范围。</p>
